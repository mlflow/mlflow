# Budget Alerts & Limits

Budget policies let you control AI Gateway spending by setting a threshold (USD) over a recurring time window (daily, weekly, or monthly). When the threshold is exceeded, the policy takes one of two actions:

- **Alert** — fires a webhook notification. Requests continue normally.
- **Reject** — blocks subsequent requests with HTTP 429. The request that causes the spend to exceed the budget is allowed to complete; rejection applies to requests that arrive after the threshold has been exceeded.

Spend is measured over either a fixed window, which resets at the start of each new period, or a sliding window, which always covers the most recent period (see [Time Windows](#time-windows)). When workspaces are enabled, budget policies can be scoped to a specific workspace so that spend is tracked per workspace.

## Alert Webhooks

When an `ALERT` policy's threshold is exceeded, the gateway fires a webhook with details about the breach. With a fixed window, the alert fires once per window: subsequent requests within the same window do not trigger additional webhooks. With a sliding window, the alert fires each time spend crosses the threshold: once enough old spend ages out for spend to drop back below the threshold, the next crossing fires another alert.

Webhook endpoints can be configured directly from the **Budgets** page under the **Budget alert webhooks** section.

The webhook payload includes:

```json
{
  "budget_policy_id": "bp-abc123",
  "budget_unit": "USD",
  "budget_amount": 500.0,
  "current_spend": 523.40,
  "duration_unit": "MONTHS",
  "duration_value": 1,
  "target_scope": "GLOBAL",
  "workspace": "default",
  "window_start": 1704067200000,
  "window_type": "FIXED"
}
```

For a sliding window, `window_start` is the start of the oldest spend still counted toward the window.

## Reject Behavior

When a `REJECT` policy's threshold is exceeded, the gateway blocks all subsequent requests to AI Gateway endpoints with an HTTP 429 response:

```
HTTP/1.1 429 Too Many Requests

{
  "detail": "Budget limit exceeded. Limit: $500.00 USD per 1 month. Budget resets at 2026-12-01T00:00:00Z. Request rejected."
}
```

For a sliding window, the response reports when enough spend will have aged out of the window for requests to be accepted again:

```
{
  "detail": "Budget limit exceeded. Limit: $50.00 USD per sliding 1 hour window. Spend falls back under the limit at 2026-11-23T14:36:00Z. Request rejected."
}
```

If usage tracking is on for the endpoint, the gateway records each rejected request as an error trace. This trace has the same user and caller metadata as a request that the gateway accepts.

## Time Windows

A budget policy measures spend over a window whose length is its duration (for example, 1 day). The policy's `window_type` decides how that window moves.

### Fixed windows

Fixed windows (`FIXED`, the default) are consecutive intervals aligned to calendar boundaries:

- **Daily** — resets every day at midnight UTC
- **Weekly** — resets every 7 days on Sundays
- **Monthly** — resets on the 1st of each month

Accumulated spend resets to zero at the start of each new window.

### Sliding windows

Sliding windows (`SLIDING`) always cover the most recent duration ending now, such as the last 24 hours, rather than the current calendar day. Spend never resets all at once: each request's cost stops counting once it is older than the duration. This matches how many LLM providers enforce rate limits, and avoids the burst a fixed window allows when its spend resets at a boundary.

The gateway tracks a sliding window in 60 buckets, each 1/60 of the duration (for example, 1-minute buckets for a 1-hour window). A cost is filed under the bucket in which its request started, and counts until that whole bucket has aged out of the window. A cost therefore counts for at least the full duration, and at most one bucket longer. For `MONTHS` durations, a sliding window covers the same span of calendar months, and buckets are sized from 30-day months.

Create a sliding-window policy by setting `window_type` to `SLIDING`, for example through the REST API:

```bash
curl -X POST http://localhost:5000/api/3.0/mlflow/gateway/budgets/create \
  -H "Content-Type: application/json" \
  -d '{
    "budget_unit": "USD",
    "budget_amount": 50,
    "duration": {"unit": "HOURS", "value": 1},
    "target_scope": "GLOBAL",
    "budget_action": "REJECT",
    "window_type": "SLIDING"
  }'
```

An existing policy can be switched between window types with the update API. Switching discards the spend tracked so far for the policy and rebuilds it from trace history.

## Authorization

When [authentication](/self-hosting/security/basic-http-auth) is enabled for the tracking server, only admin users can create, update, or delete budget policies.

## Budget Tracker Strategies

The gateway uses a _budget tracker_ to accumulate spend and evaluate budget policies on every request. Two strategies are available: `local` and `redis`.

### Local

**Pros:**

- No external dependencies — runs entirely in-process.
- Lowest latency; no network round-trips per request.
- Accumulated spend survives restarts via trace backfill on startup.

**Cons:**

- Budget state is **not** shared across workers or replicas. Each process tracks spend independently, so the total across all workers can exceed the configured limit.
- If trace backfill is disabled or unavailable, spend resets to zero on restart.

```bash
# No extra environment variables required
mlflow server --host 0.0.0.0 --port 5000
```

### Redis

**Pros:**

- Budget state is shared across all gateway workers and replicas — the limit is enforced globally.
- Atomic operations guarantee race-free window initialization and cost accumulation.

**Cons:**

- Requires a running Redis instance reachable from every gateway process.
- Adds a small per-request latency for the Redis round-trip.
- Requires an additional dependency: `pip install redis`.

| Environment Variable              | Default | Description                                                                                                                                                                                     |
| --------------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MLFLOW_GATEWAY_BUDGET_REDIS_URL` | `None`  | Redis connection URL. Setting this variable activates the `redis` strategy. Examples: `redis://localhost:6379/0` (plain), `rediss://host:6380/0` (TLS), `redis://:password@host:6379/0` (auth). |

```bash
export MLFLOW_GATEWAY_BUDGET_REDIS_URL=redis://localhost:6379/0
mlflow server --host 0.0.0.0 --port 5000
```

## Policy Refresh Interval

Both strategies periodically re-fetch budget policies from the database. The interval is controlled by `MLFLOW_GATEWAY_BUDGET_REFRESH_INTERVAL` (default: `600` seconds). Decrease the value to pick up policy changes faster; increase it to reduce database load.

```bash
export MLFLOW_GATEWAY_BUDGET_REFRESH_INTERVAL=30
mlflow server --host 0.0.0.0 --port 5000
```
