# Run code-based scorers in job containers

:::note[Experimental]

Running code-based scorers in job containers is experimental. It may change or be removed in a future release.

:::

A code-based scorer is Python code. When you [register](/genai/eval-monitor/scorers/custom) a scorer made with the `@scorer` decorator, MLflow stores the function's source code, and the server must run that code to use the scorer. By default, a self-hosted MLflow server does not run this code, because it can do anything the server process can do.

A self-hosted server can instead run code-based scorers in **job containers**: short-lived Docker containers that have no network access. With job containers, the server runs `@scorer` scorers for:

- [**Automatic evaluation**](/genai/eval-monitor/automatic-evaluations): online scoring jobs score new traces and sessions as they are logged.
- **Scorer runs started from the MLflow UI**: running a registered scorer on selected traces.

The server still finds and samples the traces, and it checks and logs the results. Only the scorer's code runs in the container.

## Requirements

- A self-hosted MLflow server with a database backend store (`--backend-store-uri`), so that the server can run jobs.
- A Docker daemon on the same host as the MLflow server. The server and the containers exchange files through bind mounts, so a remote daemon does not work. A Podman socket also works.
- A single server replica. The job execution engine that job containers need supports only one replica today.

## Set up the server

Set these environment variables before you start `mlflow server`:

| Variable                                          | Value           | Purpose                                                       |
| ------------------------------------------------- | --------------- | ------------------------------------------------------------- |
| `MLFLOW_SERVER_ENABLE_CUSTOM_SCORERS`             | `true`          | Allow the server to run code-based scorers at all.            |
| `MLFLOW_SERVER_JOB_EXECUTION_ENGINE`              | `executor`      | Use the job execution engine that supports job containers.    |
| `MLFLOW_JOB_CUSTOM_SCORER_EXECUTOR_BACKEND`       | `docker`        | Run code-based scorers in job containers.                     |
| `MLFLOW_JOB_IMAGE` (optional)                     | an image name   | The image for job containers. See [The job image](#the-job-image). |
| `MLFLOW_JOBS_DOCKER_HOST` (optional)              | a daemon URL    | The Docker daemon, for example `unix:///var/run/docker.sock`. By default, the Docker client's default is used. |

```bash
export MLFLOW_SERVER_ENABLE_CUSTOM_SCORERS=true
export MLFLOW_SERVER_JOB_EXECUTION_ENGINE=executor
export MLFLOW_JOB_CUSTOM_SCORER_EXECUTOR_BACKEND=docker

mlflow server --backend-store-uri sqlite:///mlflow.db
```

The server checks this setup when it starts. When it is ready, the server logs a warning that says the docker job executor runs custom scorers without network access.

Run the MLflow server as a non-root user. Job containers run as the same user as the server.

## The job image

Job containers have no network access, so the image must already contain everything the scorer needs:

- MLflow, with the same version as the server.
- Every package that the scorer imports.

If you do not set `MLFLOW_JOB_IMAGE`, the server builds a minimal image when it starts: a slim Python image with the server's MLflow version and nothing else. This build downloads MLflow from the package index, and it does not use your `PIP_INDEX_URL` or `PIP_EXTRA_INDEX_URL`. If your server cannot reach the public package index, or your scorers need more packages, build your own image and set `MLFLOW_JOB_IMAGE`:

```dockerfile
FROM python:3.11-slim
RUN pip install "mlflow==<the server's MLflow version>" rapidfuzz
```

If the image you set is not present locally, the server pulls it when it starts.

## Turn on automatic evaluation for a code-based scorer

Register the scorer and start it, as you would for an [LLM judge](/genai/eval-monitor/automatic-evaluations):

```python
import mlflow
from mlflow.genai.scorers import ScorerSamplingConfig, scorer

mlflow.set_tracking_uri("http://localhost:5000")
experiment_id = mlflow.set_experiment("my-app").experiment_id


@scorer
def answer_length(outputs) -> int:
    return len(str(outputs))


registered = answer_length.register(name="answer_length", experiment_id=experiment_id)
registered.start(
    experiment_id=experiment_id,
    sampling_config=ScorerSamplingConfig(sample_rate=1.0),
)
```

To read a registered code-based scorer back, the client also runs its code. So set `MLFLOW_SERVER_ENABLE_CUSTOM_SCORERS=true` where you run this code, too.

New traces get an `answer_length` assessment after they are scored. Scorers that accept a `session` argument score whole sessions, and their assessment is logged on the session's first trace. The assessments have a `CODE` source with the scorer's name.

## What scorer code can do

Scorer code in a job container runs with these limits:

- **No network access.** The scorer cannot call an LLM, an API, or any other service. A scorer that tries to connect fails, and the trace gets an error assessment, for example `[Errno 101] Network is unreachable`. To use an LLM, use an [LLM judge](/genai/eval-monitor/scorers/#llms-as-judges) instead: LLM judges keep running on the server.
- **Only the scorer function is stored.** Import the modules that the scorer uses inside the function, and use only packages that are in the job image.
- **No expectations.** Automatic evaluation has no ground truth, so it does not accept scorers that take an `expectations` argument.
- **One scorer at a time.** Automatic evaluation does not accept an ensemble that includes code-based scorers.
- **CPU and memory.** By default, each container gets 1 CPU and 1 GiB of memory. To change this, set `MLFLOW_JOB_RESOURCE_LIMITS_<job name>` to a JSON object such as `{"cpu": "2", "memory": "2Gi"}`. The job names are `run_online_trace_scorer` and `run_online_session_scorer` for automatic evaluation, and `invoke_scorer` for scorer runs started from the UI.
- **Time.** An online scoring job runs its scorers one batch at a time. A batch is up to `MLFLOW_SERVER_SCORER_INVOKE_BATCH_SIZE` traces (default 100) for a trace-level scorer, or one session for a session-level scorer. The batches of a job share its time limit, `MLFLOW_SERVER_JOB_DEFAULT_TIMEOUT` (default 3600 seconds), and each batch gets at most half of it.
- **Output size.** Each file that the scorer writes is limited to 64 MiB, and the scorer's result to 8 MiB.

The server checks each container's result before it logs anything. A container can only report results for the traces it was given, and it cannot remove assessments that LLM judges or built-in scorers logged.

## When something fails

Failures show up as error assessments on the traces, as for a scorer that fails on the server: for example a scorer that raises, a container that times out, or a job image that cannot be pulled. The server log has the details.

These cases need an operator:

- **Stopping the server does not stop running job containers.** The server removes the containers that an online scoring job left behind when it next runs an online scoring job for the same experiment, and the containers of scorer runs started from the UI when it starts again. To remove them yourself, run `docker rm -f $(docker ps -aq --filter label=mlflow.job_name=run_online_trace_scorer)`, and the same for the other job names.
- **The host disk.** The job's output directory on the host has no total size limit, so a scorer can fill the disk until its job times out.
- **Every server must use the same settings.** If a job runs on a server without `MLFLOW_JOB_CUSTOM_SCORER_EXECUTOR_BACKEND=docker`, or with code-based scorers disabled, the job skips its code-based scorers and logs a warning. It never runs their code outside a job container.
